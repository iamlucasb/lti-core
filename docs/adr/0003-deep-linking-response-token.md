# Add Deep Linking 2.0, with a response backed by the one-time store

Some platforms only send the instructor role in a deep linking request, and the custom parameters of a link only exist if the tool returns them in its Deep Linking response. We therefore add `LtiDeepLinkingRequest` to the existing launch flow: same checks on initiation, `state`, `nonce`, JWKS, issuer, audience, deployment and target. `validate` returns a union discriminated by `messageType`, which is a breaking change (0.3.0) but forces the consumer to distinguish the two messages. Roles stay raw, and optional as the specification requires; `sub` remains required, which is stricter than the 2023 revision. Authorizing an instructor belongs to the application.

The response must never be built from browser data. `validate` stores what is needed to respond (registration, deployment, return URL, `accept_types`, `accept_multiple`, `data`) in the `OneTimeStore`, and returns an opaque single-use reference, valid for one hour by default. We preferred it over an in-memory object (lost between two HTTP requests and unusable across multiple instances) and over a stateless signed token (replayable until expiry, and a second key to manage). In return, the store must keep the entry while the content is being selected. The shape of the Content Items is validated before consumption, so that a programming error does not force the deep linking flow to be restarted; only a rejection by `accept_types` or `accept_multiple` consumes the reference. `ltiResourceLink` URLs must belong to `allowedTargetLinkUris`, otherwise the next launch would be rejected.

The RS256 signing key is provided by the application, with a `kid`. The core neither generates nor stores it, never leaks it in any error, and publishes a JWKS that accepts additional keys for rotation. Only `ltiResourceLink` is supported; other Content Item types, `lineItem` (AGS), NRPS and Dynamic Registration remain out of scope. Reverting would require removing a branch of the public contract and migrating the links that were created.

Update (0.4.0): the raw `deep_linking_settings.data` value is now visible to the application through `launch.claims`, the verified payload exposed for claims the core does not interpret. This does not weaken the decision: the browser already carried the `id_token` holding `data`, so it is no secret from the user, and the response still echoes the copy stored at validation, never a value supplied by the browser or the application.
