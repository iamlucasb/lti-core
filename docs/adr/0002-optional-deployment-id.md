# Make `deployment_id` optional per registration, by explicit declaration

LTI 1.3 Core requires the `https://purl.imsglobal.org/spec/lti/claim/deployment_id` claim in every launch. Some platforms do not send it (for example, Dokeos does not send `deployment_id`), and rejecting these launches would block any integration with them. We therefore deviate from the specification, but only for a registration that declares `deploymentIdRequired: false`; the default remains compliant. The deviation only concerns this claim: issuer, audience, JWKS signature, `state`, `nonce`, target, version and message type remain required, and a `deployment_id` that is present is still validated against `deployments` (if the list is not empty) and against the `lti_deployment_id` hint of the initiation. The unsigned hint is never exposed as a deployment.

We preferred an option declared per registration over platform detection in the core or a global tolerance: the core contains no Dokeos-specific logic, and a compliant registration loses no guarantee. In return, `LtiContext.platform.deploymentId` becomes optional for all consumers (0.2.0). [ADR 0001](0001-lti-identity-scope.md) is unaffected, because the LTI identity does not contain the deployment. An application that associates business objects with an `issuer`/`clientId`/`deploymentId` integration must plan a fallback key for these registrations. Reverting would require migrating these associations.

Addendum (0.3.0): LTI Deep Linking 2.0 also requires `deployment_id` in the `LtiDeepLinkingResponse`. For a deep linking request that did not contain one (registration with `deploymentIdRequired: false`), the response omits it: the core never invents or infers a deployment, and the unsigned initiation hint is not used. See [ADR 0003](0003-deep-linking-response-token.md).
