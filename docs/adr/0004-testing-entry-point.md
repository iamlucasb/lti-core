# Publish a fake platform as a second entry point, `lti-core/testing`

Every tool built on `lti-core` needs to test its launch and Deep Linking routes without a real LMS, and each one rewrote the same fake platform: a throwaway RS256 key, a JWKS served through a `fetch` stub, ID tokens signed with the nonce of the authorization request, and a reader for the tool's Deep Linking response. We publish it as `lti-core/testing`, a second entry point, rather than in the main entry (it would put test code in every production import) or in a separate package (a second release and version matrix to keep in sync with the protocol rules it mirrors).

The fake platform is generic. Platform behaviors that deviate from the defaults are options documented on `TestPlatformOptions`, never named after a vendor: `deploymentId: null` plays a platform that omits `deployment_id` (see [ADR 0002](0002-optional-deployment-id.md)), and `roles` sets the roles sent per message type, for example a platform that only grants Instructor in a deep linking request. It only uses `jose` and Web Crypto, like the core. It does not make `lti-core` a platform implementation: it checks what a test needs, throws a plain `Error` on a protocol mistake, and is not meant for production.

It generates the platform's key, never the tool's: the rule that the library never generates or stores the tool's private key still holds, and tests create their tool key with `jose`. The `src/index.ts` rule of a single export surface becomes: `src/index.ts` for the library, `src/testing.ts` for test support, and nothing else. Reverting would break consumers' tests, which is why this is recorded here.
